# Правила работы

## Диски и исходники

- Не читать, не изменять и не удалять файлы на C: и D: без явного разрешения пользователя. Работать с проектом и артефактами на E:.
- Не обходить ограничение через WSL, ссылки, инструменты или подпроцессы. Если инструмент требует доступа к C: или D:, сначала объяснить необходимость и получить разрешение.
- Использовать только репозиторий CSQTTR и его форки. Репозиторий CSQTT запрещено клонировать и использовать как источник кода, ресурсов или эталонов. Для классики брать встроенное оформление из истории CSQTTR.
- Сохранять архитектуру и стек Kotlin/Rust. Согласовывать лишние рабочие копии, файлы, папки и зависимости. Беречь незакоммиченные правки, профили и резервные копии.

## Хранение APK

- Хранить все готовые APK CSQTTR в `E:/Сборки для csqttr`. Для каждой версии использовать отдельную подпапку с её названием, например `E:/Сборки для csqttr/59.9`.
- В подпапке версии хранить собранный APK и файл `Отчёт.md`. В отчёте указать, что изменилось в этой сборке и зачем внесено каждое изменение.

## Ветки и публикация

- Локальные рабочие ветки: `codex`, `solution`, `main`. Локальные операции Git разрешены.
- `codex` — черновик ассистента, история отдельных изменений, сравнений и откатов. Исправления и результаты их проверки фиксируются здесь.
- `solution` — принятые пользователем варианты для проверки на телефоне. Переносить из `codex` только конкретные принятые коммиты. Публиковать кандидата в `solution` репозитория Fikisq/csqttr после явного принятия пользователем.
- `main` — стабильные решения. После испытания `solution` на телефоне и явного принятия результата пользователем перенести принятое решение отдельным коммитом в локальную `main`. Отправлять в удалённую `main` только по явному разрешению.
- Отправка в удалённую `codex` Fikisq/csqttr разрешена без отдельного запроса. Остальные действия с удалённым Git, включая fetch, pull, другие push, операции с удалёнными ветками и тегами, требуют разрешения, кроме согласованного переноса принятого решения в `solution`.
- Не создавать PR в другие репозитории без явного разрешения. Разрешение на локальный коммит не означает разрешение на публикацию.

## Изменение и проверка

- Каждое отдельное изменение логики, импорта, HTML, стилей, конфигурации, документации или тестов сразу фиксировать отдельным локальным коммитом до следующего изменения. Тесты изменения можно включить в его коммит.
- Проверять состав коммита. Не включать APK, логи, резервные копии, токены, пароли и личные данные.
- Сохранять исходную точку сравнения. Не переписывать историю и не уничтожать чужие изменения при откате.
- Для просмотра и сравнения Android-интерфейса использовать Android Emulator. Не запускать Android Studio без явного запроса. Перед установкой на телефон сохранить профили, проверить копию, установку и сохранность данных. Физический телефон использовать для согласованных проверок кандидата.
- Деплой и удаление на реальном сервере выполнять только на явно согласованной цели. Happ использовать по необходимости для доступа к цели.
- Сохранять обычные логи и их разделение по сессиям. Экономию энергии подтверждать сравнительными замерами.

## Порядок работы и отчётность

- Перед каждым запросом перечитывать применимый AGENTS.md. Перед новой отдельной задачей уточнять, записывать ли её план. Продолжение согласованного плана повторного вопроса не требует.
- Хранить здесь только незавершённые планы. Внутри них отмечать выполненные пункты [x] и указывать хеши коммитов, содержащих исправление и подтверждение. После полного выполнения удалять весь план из AGENTS.md. История и подтверждения остаются в Git.
- При вопросе о поведении сверять код и коммиты `codex`, называть проверенное поведение, версию и среду проверки. Если исправление реализовано, но проверка осталась открытой, сообщать оба факта. Отдельно указывать состояние в `solution` и `main`, когда это важно для ответа.
- В отчёте указывать число и хеши сделанных локальных коммитов. Публикацию подтверждать отдельно.
